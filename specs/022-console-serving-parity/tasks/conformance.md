## Subsystem summary

Parity for increment 022 is a set of checks that a machine can evaluate. It holds at a console commit C only when all eight conditions P1-P8 pass in CI on C. Every claim is labelled "synthetic backends only".

P1 Ledger completeness. specs/022-*/contracts/parity-ledger.json has exactly one row for each of the 913 project-maya test methods at 7e68a30f. Rows are keyed file::Class::method, and the list of keys is regenerated by a static AST listing of the pinned source, not by executing it. Each row has exactly one disposition:
- rust-test: one or more cargo test paths;
- scenario: one or more differential scenario ids;
- shim: the donor test runs as-is against the Rust artifact;
- vendor-render: a vendor-template conformance case;
- web-test: a Node test of console/web;
- deviation: a D-nnn id in specs/022-*/contracts/deviations.md, with owner approval recorded;
- not-applicable: a reason from a closed list (engine-source-reads, launcher-only, needs-real-pack-or-GPU, Windows-only-process-model).
A checker resolves every reference. Test paths are checked against `cargo test -- --list` output, scenario ids against the corpus and deviation ids against the register. A dangling reference fails the build. A pinned baseline ledger, generated once by running project-maya's own suite in its tests.yml configuration, records which methods pass or skip upstream. Methods that upstream skips for lack of optional tools (OpenAI SDK, poppler, pack tokenizers, transformers, MAYA_TEST_ENGINE) still need a disposition. They are marked upstream-skipped so nobody assumes they were ever green.

P2 Rust tests green. Every rust-test referenced by the ledger passes on ubuntu-24.04 and on macos-15 (Apple Silicon) with the pinned toolchain.

P3 Differential equality. Every scenario in console/conformance/scenarios runs against two targets: the Rust binary and project-maya's own Service/serve at 7e68a30f, each driven by an equivalent fake engine. The normalized observations must be equal. An observation has five parts:
- HTTP: status, allowlisted headers, and the body compared semantically (JSON structure, SSE event sequence, NDJSON line sequence);
- the engine tape: every generate call's prompt token ids, max_new and sampling map for the in-process fake, or every stdin line for the line-protocol fake;
- persisted files under the data directory;
- the stdout lines named in the log contract;
- the process exit code.
A difference is allowed only where it carries an approved D-nnn annotation. Coverage gates apply to the corpus:
- every route and method in contracts/routes.json has at least one scenario;
- every stream format (OpenAI chat SSE, Anthropic SSE, Responses SSE, Ollama NDJSON, llama.cpp-compatible, /v1/strata/stream resume) has a streamed and a non-streamed scenario;
- every error status the donor handlers can emit (contracts/errors.json) is produced at least once;
- every environment variable and configuration key in contracts/config-inventory.json is referenced by a scenario or by a ledger row.

P4 Golden freshness. The CI job re-records the committed hermetic goldens from the pinned oracle and gets byte-identical files. A golden can therefore never be edited by hand to fit a Rust bug.

P5 Shim tests pass. project-maya's serve/test_engine_contract.py (all 10 methods) passes unmodified against the Rust fake engine binary. The selected process-lifecycle classes of serve/test_stop.py pass with only their server_cmd swapped for the Rust binary.

P6 Vendor renders byte-identical. The vendor templates and fixtures are fetched from the pinned commit and verified by sha256. console-prompt then reproduces each of the following exactly, as text and as ids:
- chat_golden.json's hf strings (10 cases);
- serve/fixtures/deepseek_v41 outputs 1-5;
- the MiniMax shared-mode prompts;
- every render_ids_other_models.json entry (count and sha256).

P7 Independent tests pass. These are the contract tests, the official-SDK client tests and the property and metamorphic tests described under independent tests.

P8 Inventories closed. A static extractor runs over the pinned source and lists four things: the os.environ names read, the SERVER_ENV and RESPONSE_ENV_KEYS tuples, the routes dispatched in make_handler, and the files written. The output must be a subset of the contracts' inventories.

"Externally observable" means these items:
- HTTP status;
- headers in the allowlist: Content-Type including charset, Access-Control-*, WWW-Authenticate, Cache-Control, Retry-After, Location, Content-Disposition, X-Accel-Buffering, and any donor-specific X-* header named in a contract;
- body semantics;
- stream event order and payloads;
- inputs the engine can see;
- files written;
- the contracted log lines;
- exit codes and signal behaviour;
- child-process lifetime.

These items are explicitly not observable, so any deviation in them needs no approval:
- connection framing: HTTP version token, Content-Length versus chunked versus close-delimited, Connection and Keep-Alive;
- the Date and Server headers;
- wall-clock timings and throughput figures;
- the order of keys inside a JSON object (diffed and reported, but advisory);
- log lines outside the contract;
- thread structure.

Hardware and OS readers (NVML, AMD sysfs and KFD, Windows DXGI/PDH, hipinfo, mixed-GPU, glm_link /proc) reach parity when the re-expressed fixture tests pass. They are labelled "unverified on real hardware". Static assets are excluded from P3, because the dashboard is adapted by design. They are covered by an asset manifest and the UI-to-server contract test instead.

## Harness design

Overview. The harness lives in a dev-only crate, console/crates/console-conformance (publish = false). It is driven by scenario files in console/conformance/scenarios/<area>/*.json, with committed goldens in console/conformance/golden/. No directory is named models, logs, dist, debug, release or target, and no fixture is named mcp.json, *.log, *.key or secrets.*. The crate builds a test-only binary called `cnf` and integration tests that use the same library. There are three layers.

1. Fake engines, equivalent on both sides
(a) In-process deterministic fake. The Rust MockEngine is a faithful reimplementation of server.py MockEngine (lines 199-240):
- Each script is encoded with parse_special plus the end-of-turn id.
- With a list of scripts, the k-th generate call gets the k-th script and the last one repeats.
- Each step checks cancel and steps are capped at max_new.
- When logprobs are asked, every token gets logprob 0.0.
- The optional tok_s pacing uses the same deterministic formula, and engine.info is {logit_bias:1, logprobs:TOP_LOGPROBS_MAX}.
The tokenizer is a Rust ByteTokenizer: one id per UTF-8 byte, with the SPECIALS list starting at 256, extendable per scenario.
(b) Line-protocol fakes. console-fake-glm reproduces glm_dsa_fake_engine.py: INFO/READY, T, STAT every 8 tokens, the 10-field DONE, the stderr banner lines, FAKE_ENGINE_IDS, FAKE_ENGINE_SCRIPT re-read at each GEN, FAKE_ENGINE_GEN_LOG, FAKE_ENGINE_IGNORE_QUIT, MAYA_GLM_SLOT_KEEP and kept-<pid>.json. console-fake-multi reproduces fake_multi_engine.py: multi=<n>, rid, interleave, PP pieces, LP lines, STOP <rid>. console-fake-mcp reproduces mcp_fake_server.py: stdio and Streamable HTTP, the tools echo, fail, sleep, big, die and add, paging, crash-at-start, FAKE_MCP_LOG. The Rust fakes are tested by running Maya's own test_engine_contract.py against them (shim) and by a cross matrix in the differential job ({Maya server, Rust server} x {Maya fake, Rust fake}).

2. Scripted behaviour expressed once
A scenario JSON is validated by contracts/conformance-scenario.schema.json. It has these fields:
- id;
- engine: {kind: mock, tokenizer: {kind: byte, extra_specials: [...]} or {kind: bpe-bytes, added: {...}}, script: [text...], max_context, info overrides, delay_ms} or {kind: line, fake: glm|multi, args, env};
- template: a project-authored template name under console/conformance/templates, or vendor:<name>, resolved at test time from the pinned project-maya checkout;
- server: {flags, env, config object, data_dir files};
- steps: a list of {request: {method, path, headers, body or body_file, http_version: 1.0 or 1.1}, disconnect_after_events, wait_for_engine_step: n, release_engine_step: n, concurrent_group};
- observe: any of http, engine_tape, files: globs, log: regex ids, exit.

The bpe-bytes tokenizer is generated at run time, like test_stop's fake_config, so no tokenizer files are committed. Substitution tokens ({{loopback}}, {{port}}, {{tmp}}, {{key_short}}) stop committed JSON from containing literal host addresses or long key values that the staged scan rejects.

Each target turns a scenario into the same inputs. The Rust side starts pulsar-console with --engine fake plus the scenario's engine spec, or with a generated --config pointing at the fake engine executable. The Maya side runs console/conformance/oracle/maya_driver.py, our own MIT code. It imports serve.server from the pinned checkout and builds Service(MockEngine-or-StrataEngine, ByteTokenizer subclass, ChatTemplate(path)). It wraps generate in a recorder that writes the engine tape, disables start_telemetry and the update check, calls serve(svc, port=0), and prints `CNF-READY port=<n>`.

Concurrency and race scenarios use engine step gates instead of sleeps. The fake blocks before step n until the harness releases it. In-process this is a control channel. For line fakes it is a FIFO file named by FAKE_ENGINE_GATE, a new environment variable implemented in both our Rust fakes and an oracle-side wrapper. This makes interleavings deterministic.

3. Starting and stopping the Rust binary
console-conformance::process does the following:
- builds or locates pulsar-console through CARGO_BIN_EXE in tests, or a path argument in cnf;
- spawns it in a new process group with a cleared environment plus an allowlist (PATH, TZ=UTC, LC_ALL=C.UTF-8, HOME and XDG_* set to a per-test temp dir, and the scenario's own variables);
- passes --port 0 and parses the ready line for the actual port, within a bounded deadline that defaults to 20 s and scales with CONSOLE_TEST_TIME_SCALE;
- captures stdout and stderr to files that CI keeps as artifacts on failure;
- on drop sends SIGTERM to the group, waits for a grace period, then sends SIGKILL, and asserts that no descendants remain. Descendants are found through a ps-free /proc or libc walk, with a libc::killpg fallback.
Process-lifecycle tests sit in one integration-test binary with a process-wide mutex. Everything else runs in parallel on port 0 with a unique temp dir.

4. Client and normalization
The client is a raw tokio TcpStream with an httparse-based reader that accepts close-delimited, Content-Length and chunked bodies. Framing is recorded as metadata but is not part of the verdict. The client can send HTTP/1.0 or HTTP/1.1 request lines and can disconnect after N SSE events or N bytes.

Bodies are parsed by Content-Type:
- application/json is parsed to JSON;
- text/event-stream is parsed to a list of {event, data}, where data is parsed as JSON when possible and [DONE] is kept literally;
- application/x-ndjson is split into a list of JSON lines;
- anything else becomes a sha256 plus length.

Normalization rules, which are themselves unit-tested with negative cases that must produce a diff:
(a) Ids. Strings matching chatcmpl-, resp_, msg_, rs_, fc_, call_, item_, toolu_ or job prefixes followed by 12-32 hex characters become <prefix#k>, numbered by first appearance across the whole scenario. A previous_response_id that refers back to a response therefore stays checkably consistent. Deterministic ids such as call_0 are left alone.
(b) Times. created and created_at integers become <epoch-s> after a check that they lie within the run window. ISO-8601 stamps become <iso> after a parse check. Duration and throughput fields (total_duration, eval_duration, prompt_ms, decode_ms, tok_s, timings.*, peak figures) become <num> after a type and non-negativity check. The field list is contracts/volatile-fields.json.
(c) Headers. Only the allowlist is compared. Header names are compared case-insensitively. Date, Server, Connection, Keep-Alive, Transfer-Encoding, Content-Length and the HTTP version are dropped.
(d) SSE keep-alive comments and queue pings, whose timing depends on MAYA_QUEUE_PING_S, are dropped unless a scenario observes them.
(e) The branding rename map, contracts/rename-map.json, is applied to the Maya observation before comparison. It covers the [maya] log prefix, MAYA_* and the Rust environment names, the maya. storage prefix and quant labels. Every entry cites a D-nnn deviation.
(f) Persisted files are parsed as JSON and normalized with the same rules. Temp paths become {{tmp}}.
(g) JSON key order is reported as advisory only.

HTTP/1.0 versus HTTP/1.1. The donor answers every request with HTTP/1.0 and ends SSE by closing the connection (server.py line 5405). The harness defaults to an HTTP/1.1 request with Connection: close, which both servers satisfy, and compares the de-framed content. A dedicated framing contract test then checks four things:
- an HTTP/1.0 request gets a complete response;
- the stream ends after its terminal event with either a connection close or a final zero chunk;
- no response relies on keep-alive state;
- a client that half-closes mid-stream causes generation to cancel, which is the donor's disconnect semantics.
Whether Rust replies HTTP/1.1 with chunked encoding or emulates HTTP/1.0 is a server-design decision recorded as a deviation, and the harness is indifferent to it.

## Differential design

Yes: project-maya's own server runs beside the Rust server in CI, as the oracle allowed by ADR 0002. It is never a build or runtime dependency.

Where it runs. Job `console-differential` on ubuntu-24.04, after the hermetic Rust job has uploaded the release binary and the fake-engine binaries as an artifact. Linux is chosen for cost and to avoid contention for the macOS runners that macos.yml already uses heavily. The donor's own CI also runs its serve suite only on ubuntu, so this is the oracle's best-supported platform.

How project-maya is obtained. actions/checkout, pinned by commit SHA, with repository mw00/project-maya and ref 7e68a30f2f208056195352129188661fb6b94445 (the full SHA, never a tag or branch). It checks out to $RUNNER_TEMP/maya, outside the workspace, so nothing can be committed by accident. persist-credentials is false, fetch-depth is 1, and the checkout is sparse: serve/, tools/, data/glm-dsa/templates/, maya.py, setup.py, VERSION and LICENSE*. A verification step follows. It asserts `git rev-parse HEAD` equals the pin. It then checks a sha256 manifest, console/conformance/oracle/maya-pin.json (commit plus the hash of every file the oracle and the vendor-render tests read). The manifest is reviewed when written, so an upstream force-push, deletion or tampering fails as ORACLE_PIN_MISMATCH or ORACLE_UNAVAILABLE, never as a parity failure. Locally, developers set CONSOLE_MAYA_SRC to their own read-only checkout. Without it, every oracle-dependent test reports an explicit SKIPPED_NO_ORACLE line, so a skip can never pass silently as green.

What must be installed. Python 3.12.x, an exact patch release, matching the donor's tests.yml, installed through astral-sh/setup-uv pinned to the same SHA macos.yml already uses. A separate console/conformance/oracle/pyproject.toml and uv.lock with exact, hashed pins of what the donor's CI installs and the server imports: jinja2 with MarkupSafe, regex, psutil, jsonschema>=4.18,<5 with its dependencies, numpy, pyyaml and tqdm. uv sync --frozen. The root pyproject.toml and uv.lock are never touched. Node is not needed in this job. Poppler is not installed, which reproduces the donor CI's skip set. An optional advisory step can add it.

What the job does, in order:
(1) Golden freshness. `cnf record --target maya` re-records every hermetic scenario that uses project-authored templates and diffs the result against console/conformance/golden. It must be byte-identical (P4).
(2) Live differential. `cnf diff --targets rust,maya` over the whole corpus, failing on any unannotated difference (P3).
(3) Cross-engine matrix. The line-protocol scenarios run four ways (Maya or Rust server, Maya or Rust fake engine). The engine tapes must match pairwise, which proves the fakes are equivalent and the adapter is faithful.
(4) Vendor renders. console-prompt's vendor test binary runs with CONSOLE_VENDOR_DIR=$RUNNER_TEMP/maya and covers chat_golden.json, the ds41 fixtures, MiniMax and render_ids hashes (P6).
(5) Shim. Maya's serve/test_engine_contract.py runs unmodified with MAYA_TEST_ENGINE pointing at the Rust fake. test_stop's server classes run through console/conformance/oracle/shim_stop.py, which imports the module and replaces server_cmd and fake_config (P5).
(6) Inventory extraction. An AST-only static script reads the pinned source and checks contracts/routes.json, config-inventory.json and the ledger key list. It never imports the donor code (P1, P8).
(7) Weekly and manual only, not per push: run the donor's complete suite (python -m unittest discover -s serve) to regenerate the baseline pass/skip ledger and detect drift in our understanding of the pin.

Acceptability under the ADRs. ADR 0002 names a differential-testing path as a sanctioned role of the Python oracle and requires that oracle code never call the implementation under test. The oracle driver only builds the donor Service and records. The comparison happens in the separate Rust cnf tool. The shim step runs donor tests against our artifact, which is a test calling the implementation, not the oracle calling it; that is permitted, and it is documented as the shim tier. ADR 0004 holds because no donor runtime becomes a PulsarMLX dependency: the donor is fetched at a pinned commit, only in CI test jobs, never vendored, never linked and never shipped. The provenance record goes in docs/upstream/PROJECT_MAYA.md, following the precedent of SSD_LLM.md (pin table, licence, module map, how the oracle is used), with attribution in NOTICE.md.

Security note: the job executes third-party code at a reviewed SHA. It runs with permissions: contents: read, no secrets, no write token, and only after the hash manifest check.

## Independent tests

ADR 0004 asks for tests that do not merely restate the donor's behaviour. Translated donor tests and the differential prove sameness with the donor. They cannot catch a bug that the Rust code and the donor share, or a bug introduced by the translator. Independent tests are written from public specifications and from the contracts in specs/022-*/contracts. The author is a different agent session from the one that ported the behaviour, and that author is told not to read the donor tests. Each test file states its source of truth. Six families:

(1) Contract tests. One per contract document: routes, errors, the SSE grammars for OpenAI chat, Anthropic Messages (message_start, content_block_start/delta/stop, message_delta, message_stop) and Responses (response.created ... response.completed, with sequence_number monotonic), the Ollama NDJSON shapes, the engine line protocol, the scenario format and the persisted-file schemas. Each contract states its invariants, and the tests check those invariants over every scenario output. Examples: every stream ends with exactly one terminal event; usage totals equal the sums of their parts; no delta is emitted after the terminal event; an error after the headers are sent is a terminal error event, never a second status line.

(2) Official-client tests. These use pinned versions of the openai and anthropic Python SDKs, in a separate locked environment, as third-party oracles. They cover chat (whole and streamed), tools, structured output through Responses parse, Responses with store, previous_response_id and background polling, and Anthropic messages with tools and thinking. They also use curl --http1.0 and an HTTP/1.1 client with keep-alive, to show framing robustness. The archived serve-synthetic crate already used pinned openai SDK smoke tests, which is precedent. The donor's own test_official_sdk methods are skipped in its CI, so this coverage is new.

(3) Metamorphic tests across dialects. For the same script, the text of the concatenated streamed deltas equals the whole response. OpenAI, Anthropic, Responses, Ollama and llama.cpp return the same assistant text and tool calls. Re-chunking the fake engine's token stream (one token per step, versus a different tokenization of the same bytes, via extra specials) does not change the output. Disconnecting at event k always leaves the server able to serve the next request, and the engine tape shows cancel.

(4) Seeded property tests. A small in-house PRNG with fixed seeds is used instead of a new proptest dependency. They cover:
- incremental tool-call parsers for every syntax (a split anywhere agrees with whole-text parsing), generalising the donor's single test_every_split_agrees_with_whole;
- SSE writer and reader round trips with arbitrary UTF-8 split points;
- the detokenizer, where any split of the ids yields the same text;
- the prompt memo, where the memoized render equals the full render for random conversations over the project template;
- the JSON-schema subset validator against hand-written accept and reject vectors taken from the JSON Schema specification text.

(5) Security and robustness, written from the threat model rather than from donor behaviour:
- authentication enforced on every route in routes.json when an API key is set (the test enumerates the inventory, so a new unprotected route fails);
- a CORS allowlist with no wildcard by default;
- the body limit (MAYA_MAX_BODY_MIB equivalent) answering 413 before the body is read, on a declared Content-Length;
- slow-header and slow-body timeouts;
- path traversal on /web static assets;
- that local-file and remote URL image inputs follow the approved deviation policy;
- that management routes which delete files stay inside the model root;
- request smuggling with conflicting Content-Length and Transfer-Encoding.

(6) Harness self-tests. Normalizer negative tests check that a deliberately changed status, header, event, id cross-reference or tape entry is detected. A mutation smoke runs the comparator with a known-buggy fake to make sure the differential can fail.

The ledger records which ADR 0004 independent tests cover each subsystem, and a work package is not done until its subsystem has at least one independent family attached.

## Lessons from the reverted serving gate

Why the serve-synthetic gate broke (revert 005867d8). Its required "Mutation guards" step (q_campaign.py rust_mutation) copied the crate and ran `cargo test --offline --locked` inside a scrubbed environment, using whatever cargo and rustc the hosted runner shipped (CI_SELECTED_CARGO and CI_SELECTED_RUSTC, with no rust-toolchain file). When the macos-15 image's toolchain moved past the 1.95.0 that passed locally, the pristine copy stopped compiling in that environment, and the step raised TOOLING_NOT_READY. The gate was already red before merge, the merge went ahead anyway, and repairing it meant changing the harness itself. Formatting and clippy with -D warnings also ran on the floating toolchain.

Rules for console:
(1) Pin the toolchain exactly in console/rust-toolchain.toml, with rustfmt and clippy components, install it explicitly, and assert `rustc -V` matches before any other step. Never set RUSTUP_AUTO_INSTALL=0 in a way that blocks the pinned install. Never rely on the runner's default toolchain.
(2) One dependency resolution per job: `cargo fetch --locked` into a single CARGO_HOME, then --frozen for every command. No nested cargo invocations, no copied crates, no scrubbed environments inside a required job.
(3) The required gate contains only checks that are deterministic functions of the repository content plus pinned tools: fmt, clippy, tests, differential at a pinned SHA, and the ledger. Meta-qualification such as mutation campaigns, latest-toolchain builds, flake hunting and upstream baseline runs is advisory and can never turn a PR red.
(4) A weekly drift canary on the latest stable toolchain and current images surfaces drift as a planned toolchain bump, done as a reviewed one-line change to rust-toolchain.toml together with any new lint fixes. Drift is never discovered as a red main.
(5) Explicit runner labels (macos-15, ubuntu-24.04) and actions pinned by SHA.
(6) Each failure has a named class and prints the toolchain, image and command, and every job can be reproduced locally with one documented command (console/ci/README section and `cargo test` or `cnf` invocations). The CI never runs a bespoke Python orchestration layer around cargo.
(7) Network-dependent steps (the oracle checkout) fail with ORACLE_UNAVAILABLE, distinct from parity failures, so an outage of the donor repository is never mistaken for a regression. The hermetic tier (J1 and J2) never needs the oracle.
(8) No merge of a console change unless console-summary is green on the PR head, with the run id recorded in the PR. The revert happened because a known-red gate was merged.
(9) Keep the workflow small. The archived gate interleaved Python campaign scripts and SDK venvs into one long job; console splits concerns into short jobs with one responsibility each.
(10) A separate workflow is not covered by macos.yml's aggregate status, and the owner must decide whether branch protection requires console-summary. Until then the gate is advisory in GitHub's eyes, and reviews must check it by hand.

## Determinism rules

- The fake engines are pure functions of (scenario, prompt, call index). They never use randomness. MockEngine's tok_s pacing keeps the donor's arithmetic formula. Default delay is 0, and timing tests assert ordering, never speed.
- Never synchronise with sleep. Interleavings are forced with engine step gates (wait_for_engine_step / release_engine_step) or with readiness lines. The donor's timing-based tests (fair slices, stall watchdog, idle unload, queue pings) are re-expressed with an injectable Clock trait in Rust unit tests. Their thresholds come through configuration as small, scaled values.
- Every bound is a deadline, never a fixed wait, multiplied by CONSOLE_TEST_TIME_SCALE (default 1, 3 in the drift canary). A test that hits a deadline prints the captured server and engine output.
- Hermetic process environment: cleared environment plus an allowlist, TZ=UTC, LC_ALL=C.UTF-8, HOME, XDG_* and the data directory in a fresh temp dir, no inherited MAYA_*, STRATA_* or PULSAR_* variables, proxy variables unset, the update check off (MAYA_UPDATE_CHECK=0 on the oracle, and the Rust equivalent, which defaults to off).
- The oracle driver turns off donor-side sources of nondeterminism: start_telemetry becomes a no-op, the update check is disabled and the port is 0. The Rust side uses a null telemetry sampler in scenarios. Host telemetry is tested only with fixtures.
- MockEngine's script turn counter is shared across requests. Multi-turn scripted scenarios are therefore strictly sequential, unless a step declares a concurrent_group with gates that fix the order.
- Bind port 0 only, and read the real port from the ready line. Never use a fixed port, and never use a free-port probe followed by a bind (a race), except in the donor-shim tests that do so themselves.
- Seeds are fixed and written in the test (the donor's random.Random(2000) answers are reproduced with the same algorithm or carried over as data). Property-test seeds are fixed in CI, and a failing seed is added to a committed regression list.
- Fixtures are generated in code (PNG, PDF, DOCX and other zip containers, byte-level BPE vocab), so no binary files are committed and the staged scan passes. Committed JSON never contains literal loopback host fields, UUID-shaped ids or key and token values of 16 or more characters; substitution tokens are used instead.
- Exact comparison for anything that does not depend on time: engine tapes, prompt ids, rendered text, tool-call arguments, logprobs from the fakes, persisted settings. Class-and-range comparison only for the fields listed in contracts/volatile-fields.json.
- Goldens change only through `cnf record --target maya` in the CI oracle environment, or locally with CONSOLE_MAYA_SRC at the pinned SHA. Each golden carries a header with the oracle commit and the scenario sha256. Hand edits are detected by the freshness check.
- Vendor templates and fixtures are read only from the hash-verified pinned checkout. A hash mismatch is a hard failure, never a skip.
- Process-lifecycle tests are serialised in one test binary. Every spawned process is in its own group and is killed on drop. A leak check after each test asserts no descendants remain.
- Pinned tools: exact Rust toolchain in console/rust-toolchain.toml, Cargo.lock with --locked and then --frozen, uv.lock with --frozen, an exact Node version, actions pinned by SHA, explicit runner image labels. No step installs anything unpinned.
- JSON key order and the HTTP framing token are reported but never decide the verdict, so the outcome cannot depend on hash-map iteration order or the transport library.

## CI jobs as proposed by the planner

- Workflow .github/workflows/console.yml. It is a new file; macos.yml is never edited. It triggers on push, pull_request and workflow_dispatch with no path filter, because skipped path-filtered jobs report success, which the archived gate rejected for exactly that reason. permissions: contents: read. Every action is pinned by commit SHA, and runner labels are explicit (ubuntu-24.04, macos-15), never *-latest.
- J0 console-preflight (ubuntu-24.04, about 1 min). Checks out the repository. Fails on any changed path outside console/, specs/022-*/, docs/ (new files only), NOTICE.md and .github/workflows/console.yml, comparing PR and push diffs against the merge base. Runs `git ls-files --others --ignored --exclude-standard console specs` and fails if anything there would be silently gitignored. Runs the repository's staged-scan rules (the read-only scripts/research/check_staged.sh logic, invoked, not edited) over the changed console files. Asserts console/rust-toolchain.toml names an exact version.
- J1 console-rust-linux (ubuntu-24.04, needs J0, about 10 min cold and 4 min warm). `rustup toolchain install <pinned> --profile minimal -c rustfmt,clippy`. Asserts that `rustc -V` equals the pin. Runs `cargo fetch --locked` once and then everything with --frozen: cargo fmt --check, cargo clippy --all-targets -D warnings (on the pinned toolchain only), cargo test --workspace (unit, re-expressed black-box HTTP, fake-engine integration, hermetic goldens, independent contract, property and security tests), cargo build --release of pulsar-console and the fake binaries, uploaded as an artifact. Cargo cache through actions/cache pinned by SHA and keyed on Cargo.lock plus the toolchain.
- J2 console-rust-macos (macos-15 arm64, needs J0, about 12 min). Same pinned toolchain and the same cargo test --workspace --frozen, without fmt or clippy. Adds the Darwin-only tests: the Apple Silicon sampler fixtures, vm_stat and sysctl parsing, signal and process-group lifecycle. Required, because the product targets Apple Silicon.
- J3 console-web (ubuntu-24.04, needs J0, about 2 min). actions/setup-node pinned by SHA with an exact Node version. Runs the translated page-logic tests (state.js, server.js, chats.js, turbo-core.js, monitor.js) against console/web under node --test, with no npm install and no dependencies. Checks the asset manifest and licence files (OFL.txt, LICENSE.lucide, Apache-2.0 text for htm) and that no binary asset is tracked unless approved. Runs the UI-to-server contract check: endpoints extracted from the JS are compared with contracts/ui-api.json and contracts/routes.json.
- J4 console-differential (ubuntu-24.04, needs J1, about 12-15 min). Downloads J1's binaries. Checks out project-maya at the pinned SHA, sparse, into RUNNER_TEMP. Verifies maya-pin.json. setup-uv pinned and `uv sync --frozen` of console/conformance/oracle. Then, in order: golden freshness, live differential over the corpus, the cross-engine matrix, vendor renders, the shim tests, inventory and ledger extraction. JUnit and diff reports are uploaded as artifacts. Failure classes are named: ORACLE_UNAVAILABLE, ORACLE_PIN_MISMATCH, GOLDEN_STALE, PARITY_DIFF, LEDGER_INCOMPLETE.
- J5 console-sdk-clients (ubuntu-24.04, needs J1, about 4 min). A separate locked environment, console/conformance/sdk, with exact openai and anthropic SDK pins. Runs the independent client tests against the J1 binary.
- J9 console-summary (ubuntu-24.04, needs J0-J5, if: always(), seconds). Fails unless every needed job succeeded. It is the single check name the owner can mark as required in branch protection. J4 is required from CNF-09 onward. Until then it runs with continue-on-error and its status is reported, not required.
- Advisory, not required. J6 console-drift-canary: workflow_dispatch plus a weekly schedule. Latest stable toolchain and the current macos-15 image, build plus test, three repeated runs of the test suite to catch flakes. Opens nothing automatically; its result is read by a person.
- Advisory, not required. J7 console-mutation: workflow_dispatch only. cargo-mutants installed with `cargo install --locked` at an exact version, run on console-prompt parsers and console-http framing; the report is an artifact. J8 console-oracle-baseline: weekly and manual. Runs the donor's full serve suite at the pin to regenerate the upstream pass/skip baseline.
- Order and cost per push: J0, then J1, J2 and J3 in parallel, then J4 and J5, then J9. About 20-25 minutes of wall time, about 30 Linux runner minutes and about 12 macOS minutes. Every push also triggers macos.yml's full native qualification, because its classifier sends unknown paths to full mode. That cost and coupling cannot be avoided without editing a frozen file, and is listed as a risk.
